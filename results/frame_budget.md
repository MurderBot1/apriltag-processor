# Frame drop model, architecture A3

Generated by `py -3.12 tools/frame_budget.py` (everything below the "Model output" heading) from the Cortex-M33 estimates of `tools/m33_cycles.py` (tag unit, the real RTL-chain packets of the 100 frames) and `tools/m33_pose_cycles.py`. **ESTIMATES from an emulated M33, not measurements on an RP2350.** The 10 frames of each category repeat as a stream at 120 fps (2000 frames); "lost" = a packet found no free frame buffer when it started. Old design for comparison (`results/tpu_budget_by_category.md`, TPU in the FPGA): 20 of 100 frames exceeded one frame period.

## Decision

**Production design: 3 frame buffers, one core, the buffer is released as soon as the tag unit has copied its tags out (before the pose solve)** = design `single_early`, `AT_NBUF = 3` in `firmware/core/atframe.h`.

| design | nominal, float pose | pessimistic, float pose | nominal, software-double pose | pessimistic, software-double pose |
|---|---|---|---|---|
| first build: 2 buffers, 1 core (`single`) | 2.0 % | 3.0 % | 3.0 % | 6.0 % |
| 2 buffers, 2 cores alternating (`alt`) | 2.0 % | 3.0 % | 3.0 % | 6.0 % |
| 2 buffers, buffer released after the tag unit (`single_early`) | 1.0 % | 2.0 % | 1.0 % | 3.0 % |
| **3 buffers, 1 core, early release (`single_early`)** | **0.0 %** | **1.0 %** | 0.0 % | 1.0 % |
| 3 buffers, 1 core, release at the end (`single`) | 0.0 % | 1.0 % | 0.0 % | 2.0 % |
| 3 buffers, core 0 tag unit + core 1 pose (`pipe`) | 0.0 % | 0.0 % | 0.0 % | 0.0 % |

(all 100 frames, "all" rows of the tables below.) The firmware solves the pose in single precision (`AT_REAL float`, FPU), so the float columns apply; the software-double columns are the bracket for the case that the solver is later switched to doubles.

Why: three buffers fit in SRAM (below), remove almost all drops in the model with a change that touches only buffer bookkeeping and the order of two calls, and keep the single cooperative loop (no locking between cores, flash programming still only has to stop core 0). The remaining 1 % (pessimistic cycle model, float pose) is the single slowest frame of one category recurring every 10th frame; it disappears with the two-stage `pipe` design (core 1 runs the pose solve on the tag list, core 0 only the tag unit). That is NOT implemented: it needs the second core brought up, shared `at_app_t` state and `flash_safe_execute` with two cores, and the numbers above are only estimates. Do it only if hardware shows drops (see "Needs hardware").

### SRAM budget (RP2350: 512 KiB striped SRAM + 2 x 4 KiB scratch banks, 520 KiB in total)

| item | bytes |
|---|---|
| 3 frame buffers, 3 x 132,128 (one packet = 33,032 words) | 396,384 |
| tag unit tables (`g_key`, `g_head`, `g_ids`) + pose workspace + flash staging 3 x 4 KiB (compiled for the PC: bss of `attpu.o` 65,728 + `atpose.o` 3,136 + `atapp.o` 12,288) | 81,152 |
| `at_app_t` (PC build 4,720; smaller on the 32-bit target) | <= 4,720 |
| subtotal of this repo's statics | <= 482,256 (471 KiB) |
| 2-buffer image as linked in the earlier session (`docs/fpga.md`: bss 348 KB incl. TinyUSB / SDK) + 132,128 for the third buffer | 480,000 - 488,500 depending on KB = 1000 or 1024 |
| 512 KiB main SRAM = 524,288 | free: about 36,000 - 44,000 (7 - 8 %) |

The packet is already bit-packed (1 bit per pixel mask 128,000 B + 4 KB candidate list + header/trailer); there is no smaller layout without losing the full-resolution mask. The core stacks sit in the two 4 KiB scratch banks (SDK default). **Not linked in this environment (no arm-none-eabi-gcc / Pico SDK here): the 3-buffer image size is computed, not taken from a linker map.** The firmware CI build should print `arm-none-eabi-size` and the map must be checked: if the image does not fit, the fallback is 2 buffers + `pipe`/`single_early` (1.0 % nominal).

### Needs hardware (nothing of the above is a measurement on the RP2350)

* real run time of the tag unit and pose on the M33 at 150 MHz with the DMA writing SRAM at 21 MB/s (bus arbitration), compared with the nominal / pessimistic columns;
* the late claim at the rising edge of `mcu_fs` (`late_claim` in `hal_frame_rx.c`): it lets a packet use a buffer that was released in the 1.7 ms gap before it. If the first word can arrive before the interrupt runs, the guards (transfer count unchanged, RX FIFO empty) keep the sink and the packet is counted lost; the one-word race is repaired by the existing `fs_check` resync. Not testable without the FPGA frame bus;
* the drop counter itself (`frames dropped` in STATUS, `max_depth` = most packets waiting or in processing) under the real 120 fps stream.

## Model output

frame period 8.328 ms; per category the 10 frames repeat (2000 frames); "lost" = frames with no free buffer when their packet starts.
TPU run times: tools/m33_cycles.py (C tag unit, 150 MHz, -O3); pose: tools/m33_pose_cycles.py (float = FPU single precision, double = software doubles).
ESTIMATES from an emulated Cortex-M33, not measurements on the RP2350.

* `single`: one core: tag unit + pose, buffer held until both done
* `single_early`: one core: tag unit + pose, buffer released after the tag unit
* `alt`: two cores alternating frames (tag unit + pose each)
* `pipe`: core 0 tag unit, core 1 pose (two-stage pipeline)
