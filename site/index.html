Overview (README)

rendered from README.md

AprilTag camera: custom vision chip + 120 fps global-shutter camera, one USB-C cable

A self-contained camera that detects AprilTags (tag36h11) at 1280x800 / 120 fps and hands back the camera's pose in a world frame you define. You send it the tags you use and where they are (plus the lens calibration) once; it stores them in flash and then streams the camera position and orientation over the same USB-C cable that powers it.

OV9281 (MIPI, 120 fps) -> ECP5-45F FPGA running custom RTL (threshold, despeckle, labelling, frame streamer) -> 8-bit frame bus ->
                          RP2350 MCU (tag decoder in C, pose solve, USB, stored field map) -> host

Nothing here is a stock vision pipeline: the per-pixel work is hardware designed in Verilog in this repo, the per-tag work (sub-pixel corner fitting, tag36h11 decoding) is C code in this repo that runs on the MCU on the binary frame the FPGA streams to it (architecture "A3", docs/costdown.md; it started life as a custom FPGA processor, the TPU, kept in ref/tpu as the bit-exact reference). The host only sees the tag estimates and poses, never an image.

Using it

import sys; sys.path.insert(0, "host")
from apriltag_cam import Camera, load_json
with Camera.open_serial("COM5") as cam:               # USB-C CDC serial port
    cam.set_calibration(load_json("config/camera_calibration.json"))
    cam.set_field(load_json("config/tag_map.json"))   # tag ids, sizes, 3D positions + orientations (quaternion wxyz)
    cam.commit()                                      # stored in flash; survives power cycles
    for pose in cam.stream():                         # ~120 Hz
        print(pose.frame_id, pose.position, pose.quaternion, pose.ntags, pose.rms_px)

Protocol: docs/protocol.md. Conventions (world, tag, camera frames, corner order) are at the top of tools/geom.py.

Headline results (details and caveats in docs/verification.md, docs/fpga.md, docs/hardware.md)

  • 120.08 fps sustained in full-chip simulation at true sensor timing (832,800 clocks per frame at 100 MHz), every frame leaves the FPGA as a complete packet; the MCU has two frame buffers so capture never stalls.
  • 100 rendered frames (10 conditions x 10) through the simulated chip + the MCU's solver: median camera position error about 1-3 mm and 0.02-0.05 deg where tags are found; 87 % of the detectable tags overall (562 / 647; the reference AprilTag library: 97 %), (identical to the previous all-FPGA design, tag by tag), up from 70 % before the noise-robust labeller - 100 % on normal / dark / grad / noise, 97 % clutter, 90-92 % blur / persp / shadow, but still 0 % on the low-contrast category, see docs/verification.md.
  • GitHub Actions: one check per dataset category (N/10 detected, reference detector) plus an all-tests workflow, see docs/verification.md.
  • RTL is verified bit-exact against Python golden models (threshold, despeckle, labelling), the C tag unit bit-exact against the golden model of the old FPGA processor, and the whole chain is exercised with real CSI-2 packets and a bit-level D-PHY model with lane skew and clock offsets.
  • Open-source place-and-route onto the real ECP5-45F pins: 12.2 k LUT4 (27 %), 56 of 108 block RAM, core clock closes 85.7 MHz on 4 of 6 seeds, D-PHY 200 MHz on 6 of 6 (docs/fpga.md).

Honest limits - read before building hardware

  1. Not run on silicon. Everything is simulated or tool-checked; there is no physical board. The ECP5 D-PHY receiver (LVDS gearing, sync hunt) and the OV9281 bring-up are the first things to validate on a prototype.
  2. OV9281 footprint: the ball map comes from an open-hardware reference design, but the CSP ball pitch/pad size is assumed (0.5 mm / 0.25 mm). Verify against OmniVision's drawing before ordering. Bare-CSP assembly with an M12 holder needs a specialist assembler.
  3. Timing closure: see docs/fpga.md for the measured fmax of each clock domain against the 100 MHz / 200 MHz targets. Anything reported as failing there must be fixed (more pipelining) before relying on 120 fps in hardware.
  4. Detection is weaker than the reference library at long range (> ~3.5 m for 16.5 cm tags), for low-contrast scenes (0 % on the lowcon category with the reset THRESH ratio; 100 % with ratio 2, see results/lowcon_ratio.md) and for small / grazing / shadowed tags. The labeller no longer rejects busy frames (256 runs/row, label recycling, the 64 largest candidates kept), but a cluttered or noisy frame costs the MCU up to about 9 ms (estimate, Cortex-M33 emulation, median 1.6 ms; the old FPGA processor needed up to 30 ms): in a stream at 120 fps a heavy frame can make the MCU miss a packet (frames_dropped); the model predicts 1 - 4 % of frames if every 10th frame were the slowest of its category (results/frame_budget.md; the old design: 20 %). The MCU timing, the PIO/DMA frame capture and the bus timing margin are not measured on hardware.
  5. No schematic capture: the board is netlist-first (pcb/design.py, pcb/output/netlist.txt).

The FPGA does everything that is per pixel and streaming: it never stores a frame. The binary (thresholded, despeckled) frame leaves it at the pixel rate together with the candidate list of the labeller; the MCU receives it into SRAM, decodes the tags (sub-pixel corners, tag36h11 match, firmware/core/attpu.c), solves the camera pose from the stored field map, and streams it to the host. (Architecture "A3" of docs/costdown.md: this is what lets the FPGA be the 45k-LUT part instead of the 85k one. The old design ran the tag decoder in a custom FPGA processor, the TPU, and held two frame banks in block RAM.)

Where the tag decoder runs, and why it is bit-exact with the old FPGA processor

The decoder is a small fixed program with a lot of fixed-point multiply/divide and pixel look-ups. It was first built as a custom FPGA processor (the TPU, ref/tpu/tpu_core.v, program tools/tpu_prog.py, golden Python model tools/tpu_isa.py), which needed 10 k LUT4, 8 block RAMs and, with the two 1 Mbit frame banks it read, most of the 85k-LUT part. firmware/core/attpu.c is a line-by-line port of that program to C (Q16.16 integer arithmetic, 64-bit multiply/shift, 48/32-bit divide on the Cortex-M33's 32-bit divider, a bucket index instead of scanning all 2,348 tag codes). tests/test_fw_tpu.py checks the whole result image against the ISS word for word on all 100 dataset frames (and thresholds, corrupted masks, random candidate records); the RTL chain (tests/run_chain_dataset.py) gives the same tags and corners as the old all-FPGA chain on every one of the 100 frames (0 px difference). The ISS is itself checked against the old RTL (tests/test_tpu.py), so the C code is transitively equal to the hardware it replaced.

Timing budget at 120 fps

OV9281 settings (tools/ov9281_init.py, register values from the mainline Linux driver): 400 MHz DDR link = 800 Mb/s per lane, 2 lanes, RAW8 -> 200 Mpixel/s; HTS = 1600 px, VTS = 1041 lines -> 200e6 / (1600 x 1041) = 120.08 fps.

  • byte clock = 100 MHz; 2 pixels per clock; one line = 800 clocks (640 carry pixels), frame = 832,800 clocks (8.328 ms)
  • threshold + CCL are paced by the line rate; the labeller needs about 2-4 clocks per run on the common path (a run that just extends the label of the run above it), 256 runs per row are kept, and up to 4 rows (2 pending + current + previous) may be in flight, so even a 100-140 runs-per-row noise frame (113,759 runs, slowest row 590 clocks) fits the 686-clock line of the real 85.714 MHz core. Unions of several components, new labels and finished components cost more (10-20 clocks each); a row that still cannot be labelled in time is dropped with a flag (max_row_cycles is exported in the status registers) - never a hang. 7 of 500 frames of an earlier (historical) evaluation set lose 1-5 rows that way, none of the current 100, see docs/verification.md
  • three frame buffers in the MCU's SRAM (3 x 132,128 B = 396,384 B, AT_NBUF in firmware/core/atframe.h): frame N is processed by the tag unit (median 1.6 ms, worst 9.3 ms, estimated) while frames N+1 and N+2 can stream in, so capture never stalls; the buffer is handed back as soon as the tag unit has copied its tags out (before the 1.8 - 3.6 ms pose solve), and a buffer released between two packets is still used by the next one (late_claim, rising edge of mcu_fs). A packet is lost (and counted, frames dropped in STATUS) only if all three buffers are busy when it starts. Estimated drops (emulated M33, not measured): 0 % nominal, 1 % pessimistic (the slowest frame of one category) with the first-build 2 buffers at 3 %; SRAM about 480 - 488 KB of 512 KiB (computed, not linked here). Decision, SRAM budget and the dual-core alternative: results/frame_budget.md
  • end-to-end latency (last pixel -> tag list on the MCU) = 17-row threshold delay + 1 row despeckle + ~2-3 rows CCL + the candidate list (~0.2 ms) + tag unit time

address content

Pose solve (MCU)

firmware/core/atpose.c: corner pixels -> undistort with the stored calibration -> homography pose of the largest tag -> Levenberg-Marquardt over all tag corners (6 DoF, analytic Jacobian) -> planar-ambiguity second start for single tags -> leave-one-out outlier rejection. Output: camera position and orientation in the world frame defined by the field map. Float32 build is what runs on the RP2350 (single-precision FPU).

Things that must be checked before ordering boards

These are limits of what could be verified without the physical parts and the vendor documents; they are listed rather than hidden:

  1. OV9281 CSP footprint (OV9281_CSP in build_pcb.py): the ball map comes from the open-hardware reference design above, but the ball pitch (0.5 mm) and pad size (0.25 mm) are assumptions. Replace with the dimensions from OmniVision's package drawing. Bare-CSP sensor assembly with a lens holder also needs a specialist assembler (active alignment/focus); the optical stack (M12, CIL023 f = 2.2 mm, 82 deg rectilinear HFOV, CLA021 holder) is in housing/README.md.
  2. ECP5 IDDRX2F bit order and the D-PHY SoT hunt are verified against a behavioural model only. The receiver tries both nibble orders so it does not depend on the convention, but it has not been run on silicon; bring-up should start with the status/lock bits of dphy_rx (LED) and the CSI-2 ECC/CRC counters in the registers.
  3. No external schematic capture: the design is netlist-first (pcb/design.py); pcb/output/netlist.txt and bom.csv are generated from it. ERC-style checks (single-pin nets, power pin coverage) are in tests/test_pcb.py.
  4. The RP2350 slave-SPI FPGA configuration opcodes (firmware/rp2350/fpga_config.c) come from memory of Lattice TN1260 and are unverified.

Architecture A3 board status (2026-11-01, production-readiness pass)

pcb/design.py (netlist source of truth) has U1 = LFE5U-45F-8BG381C (same CABGA-381 footprint; tools/pin_compat.py: all 31 used balls have the same bank and pad function as on the 85F) and the 10 frame-bus nets FB_D0..FB_D7, FB_CLK, FB_FS (FPGA bank 6 outer ball row facing the MCU <-> RP2350 GPIO16..25). The board was re-routed completely with the repository's grid router (pcb/route_sweep.py, seed 128).

Production pass (pcb/fix_power_links.py, pcb/apply_prod.py, tests/test_pcb_erc.py):

  • Unconnected items. KiCad DRC reported 10 unconnected items. They were not harmless: the router treats "pad + via" as connected to the +3V3 plane on In2, but In2 also carries signals and the +1V1 island, and the +3V3 pour is cut into islands by the BGA via lattice and by signal tracks. Six +3V3 pad clusters (U1 balls L6/L7/M6, P9, P10, L14/L15/M15, capacitors C2, C4, resistor R2, and U2 pads 20 and 11, two RP2350 IOVDD pins) hung on vias that touch no pour and so were electrically floating, and two GND pairs (C48 pad 2, U1 P11/P12 vias) were likewise split. After: 0 unconnected items, no clearance / short / hole violations.
  • Dangling vias (24 left, was 26). These are plane-stitch vias at power pads whose pad is connected by other copper (DRC reports no unconnected item for them); harmless.
  • Remaining DRC items are silk overlap (9), silk over copper (32), dangling vias (24), 2 library-footprint warnings (sensor and lens-holder placeholders): all cosmetic.
  • Lens holder screw holes are 1.9 mm (M1.6 self-tapping screws bear on the FR4); they were 2.6 mm.
  • Parts: flash label W25Q128JVPIQ (WSON-8 package), LDOs U6/U8 = ME6211C25M5G-N / ME6211C28M5G-N (same SOT-23-5 pinout, in stock), crystal load check in docs/bom/bom.json (CL = 15*15/30 + 3 pF stray = 10.5 pF for the 10 pF ABM8-272-T3).

How it got there: an incremental route (pcb/route_a3.py, pcb/ripup_region.py: keep all other copper, rip up the 20-25 signal nets crossing the MCU's left/bottom escape area, re-route with pcb/router/router14.exe) routed only 9 of the 10 nets whichever MCU pad, FPGA ball or seed was used (the 7th data bit stayed open; Freerouting 2.1.0 with fixed copper timed out). The full re-route found complete solutions on a minority of seeds; seeds 11, 36 and 128 had no router violations and 128 had the best KiCad DRC (11: 73 + 15, 36: 75 + 23). One router flaw is patched after the fact: the +1V1MCU stub on the 0.2 mm DVDD pad is narrowed from 0.3 to 0.2 mm (clearance to the neighbouring QFN pads); pcb/router/export_problem.py now also treats In2 copper as an obstacle (needed for incremental routing). The 3D renders and the site PCB pages were regenerated from the new board.

MCU frame bus (FPGA -> RP2350)

The mask is streamed at the pixel rate instead of being stored: one byte per 4 core clocks = 21.4 MB/s while a row is flowing, 15.4 MB/s average. Pins (bank 6, 3.3 V, the outer ball row on the MCU side, LVCMOS33 DRIVE=8 SLEWRATE=FAST, balls checked identical on the 85F / 45F / 25F by tools/pin_compat.py): mcu_d[7:0] = P1 N1 M1 L1 K1 P2 N2 L2 -> RP2350 GPIO16..23, mcu_clk = K2 -> GPIO24, mcu_fs = M3 -> GPIO25.

signal meaning
mcu_d[7:0] byte, changes 1 core clock before mcu_clk rises, stable for 3 clocks after
mcu_clk strobe, high 2 of the 4 clocks of a byte slot; stops (while mcu_fs stays high) if the next word is late
mcu_fs high from before the first byte of a packet to after the last

One packet per accepted frame, 132,128 bytes, little-endian words: 4-word header (0x4D335441 "AT3M", sequence number, 64-bit device time of the frame start), 32,000 mask words (800 rows x 40 words, bit x%32 of word y*40+x/32 = pixel (x,y), 1 = black, after threshold and despeckle), a 4-word trailer (candidate count, labeller flags, status bits, frame sum for auto exposure, max row clocks, check word ~seq) and the 64 x 16-word candidate records of run_ccl. A frame with a sensor CRC/line-count error still leaves as a complete packet with the CSI bad status bit (the FPGA has no store to retract it; a frame with missing lines is zero padded); the MCU discards flagged packets. Format: rtl/mask_stream.v, firmware/core/atframe.h.

RP2350 side (firmware/rp2350/frame_rx.pio, hal_frame_rx.c): a PIO state machine samples D on the rising edge of the strobe (3 PIO cycles per byte, 7 available at 150 MHz), autopush every 4 bytes, a DMA channel moves each packet (33,032 words) into one of three 132 KB frame buffers in SRAM (AT_NBUF); the channel is re-armed from its completion interrupt (to a dummy word when all buffers are busy, so the stream never loses alignment) and switched to a buffer that became free in the gap when mcu_fs rises (late_claim); a packet that ends early is detected 100 us after mcu_fs falls and repaired by restarting the state machine. Firmware RAM use: 348 KB bss of 520 KB with two buffers (linked locally); with three buffers about 480 - 488 KB of the 512 KiB main SRAM (computed, see results/frame_budget.md, not linked).

Not verified on hardware: the input timing margin (the PIO input synchroniser adds about 13 ns; the data window around the strobe edge is 11.7 ns before / 35 ns after), DMA/CPU SRAM arbitration at 21 MB/s while the tag unit runs, the PIO program itself (no PIO simulator was available; it compiles with the Pico SDK's pioasm). Testbenches: tb/tb_mstream.v (byte timing, stability around the strobe, FIFO, late labeller, short frame, abort), tb/tb_cam.v (whole chip).

Protocol

rendered from docs/protocol.md

AprilTag camera USB protocol

Transport: USB-C CDC serial (virtual COM port; baud rate is ignored). The link is a plain byte stream, so every message is framed. Source of truth: firmware/core/atproto.[ch], firmware/core/atapp.c; host implementation host/apriltag_cam/protocol.py. tests/test_fw_proto.py::test_doc_* checks the tables below against atproto.h.

All multi-byte integers and floats are little endian; floats are IEEE-754 binary32.

1. Framing

frame (on the wire) = COBS( type[1] | body[0..256] | crc16[2] ) | 0x00
  • type: message id (tables below).
  • crc16: CRC-16/CCITT-FALSE (poly 0x1021, init 0xFFFF, no reflection, xorout 0) over type | body, stored low byte first. Check value: crc16("123456789") = 0x29B1.
  • COBS: standard Consistent Overhead Byte Stuffing (a code byte 0xFF means 254 data bytes follow and no implicit zero). The encoded data contains no 0x00 byte, so 0x00 is an unambiguous frame delimiter and resynchronisation point.
  • Maximum body 256 bytes (AT_MAX_BODY); the receiver buffers 264 bytes of encoded data (AT_MAX_FRAME).
  • Receiver: bytes are collected until 0x00. An empty frame (consecutive 0x00) is ignored. A frame that overflows the buffer, fails COBS decoding, is shorter than 3 decoded bytes, or fails the CRC is dropped (and counted) without any reply. Garbage before a frame is harmless if a 0x00 separates it from the frame; a host should therefore send a lone 0x00 before the first command after (re)opening the port.
  • Request/response: the device answers every command with exactly one frame (ACK, NAK or a typed response). Commands are idempotent, so a host may retry on timeout. While streaming is enabled, unsolicited POSE frames are interleaved.

3. Commands

0x01 PING -> 0x81 PONG

Request: token[4] (anything shorter than 4 bytes is answered with a zero token). PONG: token[4] | fw_version u32 (0x00010000 = 1.0.0) | fpga_id u32 (0x41544731 "ATG1" when the FPGA is configured and alive, else 0).

0x02 SET_CALIB (RAM only, until COMMIT)

fx f32 | fy f32 | cx f32 | cy f32 | k1 f32 | k2 f32 | p1 f32 | p2 f32 | k3 f32 (OpenCV model, pixels; pixel centre of the top-left pixel is (0,0)). NAK RANGE if fx <= 1, fy <= 1 or either is NaN.

0x03 CLEAR_MAP

Empties the field map (RAM). Body ignored.

0x04 ADD_TAG

id u16 | size f32 (edge of the black square, m) | pos x,y,z f32 (tag centre in world, m) | quat w,x,y,z f32 (tag->world). Tag frame: x right, y up, z out of the printed face; world is Z up. Adding an existing id replaces it. NAK FULL when 64 tags are stored and the id is new.

0x05 COMMIT

Writes calibration + map to flash (alternating slots, see section 6) and reads it back. ACK on success, NAK FLASH otherwise (the previous stored configuration is untouched). Takes up to ~100 ms (flash erase); hosts should allow >= 3 s.

0x06 GET_CONFIG -> CONFIG

fx fy cx cy k1 k2 p1 p2 k3 (9 x f32) | ntags u16 | reserved u16 (0).

0x0C GET_TAG -> TAG

Request index u16 (0 .. ntags-1, else NAK RANGE). TAG: id u16 | pad u16 (0) | size f32 | pos 3 x f32 | quat w,x,y,z 4 x f32 (quaternion is re-derived from the stored rotation, so it can differ from the sent one by float rounding and overall sign).

0x07 STREAM

enable u8 | divider u16. When enabled the device sends one POSE frame for every divider-th successfully solved FPGA frame (divider 0 is treated as 1). Disable with enable = 0.

0x08 SET_SENSOR

exposure u16 (sensor lines, 1..800) | gain u8 (register value, 0x10 = 1x, >= 0x10). Writes OV9281 registers 0x3500..0x3502 (exposure << 4), 0x3509 (gain) through the FPGA I2C bridge with group hold. Disables auto exposure. NAK RANGE when out of range.

0x0E SET_AE

enable u8. 1 re-enables auto exposure (starting from the current exposure/gain), 0 disables it. Auto exposure is on after boot: the target is mean brightness 110 (0..255, from FPGA register FRAME_SUM / 1,024,000), deadband +-12, exposure preferred up to 400 lines then gain up to 0xFF, at most 4x change per step, one frame skipped after every change.

0x09 GET_STATUS -> STATUS (48 bytes)

offset type field
0 u32 FPGA STATUS register: frames_sent[31:16] candidates[15:8] init_done[3] stream_busy[2] 0[1] any_frame[0] (architecture A3: frames_sent counts frame packets streamed to the MCU, candidates is the count of the last packet; the bits keep their positions from the old design, where bit 2 was tpu_busy)
4 u32 FPGA CCL register (0x28): max_row_clocks[31:16] flags[11:8] candidates[7:0]. The flags are diagnostics of a degraded frame, never a rejection: bit 8 a row was dropped (labeller too slow for a very busy row), bit 9 a row had more than 256 runs (extra runs ignored), bit 10 the 1024-entry label table was full (the affected runs stayed background), bit 11 more than 64 candidates were found (only the 64 largest by area are kept). The frame is processed and its tags reported in every case; candidates is the number handed to the tag unit (0 is valid).
8 u32 frames dropped: FPGA register 0x30 (sensor frames not accepted) + packets the MCU could not receive (no free frame buffer, resync)
12 u32 frames total (FPGA register 0x34: sensor frames seen)
16 u32 frames processed (packets run through the tag unit on the MCU)
20 u32 pose solutions computed
24 u32 solver failures (no known tag / degenerate / no convergence)
28 u32 rejected frame packets (malformed, or flagged by the FPGA as damaged: sensor CRC / line-count error, FIFO overflow, short mask, labeller timeout). Legacy name torn_reads; there is no result bank to tear any more
32 u32 frame id of the last processed result
36 u16 tags in the map
38 u8 last pose valid
39 u8 streaming enabled
40 u16 current exposure (lines)
42 u8 current gain register
43 u8 auto exposure enabled
44 u16 last mean brightness x 256
46 u16 reserved (0)

0x0A SET_TRACK

diff u8 | abs_black u8 | mindim u8 | maxham u8 (bits 5:0) + ratio (bits 7:6), written to the FPGA THRESH register (0x0C): local contrast threshold, absolute black level, minimum tag dimension in pixels, maximum accepted Hamming distance. The first three are used by the FPGA; maxham is kept by the MCU (the tag unit runs there) and stored in the FPGA register for read-back only. Reset values 24, 64, 10, 2, ratio 0.

The fifth parameter is the tile contrast-ratio field ratio (bits 7:6 of the fourth byte; the message stays 4 bytes, clients that send maxham <= 63 get ratio 0), written to THRESH bits 31:30 (reset 0). A tile only gets the adaptive threshold ("contrasty") if diff >= diff_min and k * diff >= max with k = 2 / 3 / 4 for ratio 0 / 1 / 2 (ratio 3: no ratio test). The reset value k = 2 means min <= max / 2; a frame whose contrast is compressed so that black stays above half of white (the lowcon dataset category: black ~69, white ~167) has no contrasty tile and the chip then sees nothing. SET_TRACK with ratio 1 or 2 fixes that (set_track(..., ratio=2) in the Python API, set_tracking_params(ratio=2) in the host module; C++ / Java / Rust likewise). The default stays 0 because it is the more robust setting for very noisy frames (see docs/verification.md). Every SET_TRACK sets all fields, so one that omits ratio resets it to 0.

0x0B GET_POSE -> POSE

Latest solved pose. NAK NO_POSE if none yet.

POSE (52 bytes), also the unsolicited streaming message:

offset type field
0 u32 frame id (FPGA packet sequence number of the source frame)
4 u32 processing time on the MCU, microseconds: tag unit + pose solver
8 u8 tags used by the solution
9 u8 flags: 1 ambiguous (planar ambiguity unresolved), 2 outlier tag dropped, 4 single tag
10 u16 tag observations in the frame (before filtering)
12 3 x f32 position x, y, z (m), camera to world: p_w = R q + t
24 4 x f32 quaternion w, x, y, z of R
40 f32 reprojection RMS error (pixels)
44 u64 capture timestamp: device clock (microseconds) at the start of the source frame (see GET_TIME)

Camera frame: OpenCV (x right, y down, z forward). World Z up.

0x0F GET_TIME -> TIME

Device clock. The FPGA runs a free-running 64-bit counter at tick_hz = 1,000,000 Hz (1 us per tick) from FPGA reset; it never stops and never wraps in practice (584,000 years). Every frame start (CSI-2 frame-start packet) latches the counter, and that value is the frame's capture timestamp (POSE offset 44).

TIME (20 bytes): now_us u64 | frame_us u64 | tick_hz u32. now_us is the counter when the MCU served the request, frame_us is the timestamp of the newest frame whose result has been processed (0 before the first), tick_hz is 1000000 (hosts must use it instead of assuming). Host-side offset estimation: take t0 before send and t1 after the response; device time now_us corresponds to host (t0 + t1) / 2 to within half the round trip.

0x0D GET_TAGS_RAW -> TAGS

frame_id u32 | count u8 | count x { id u16 | hamming u8 | 4 corners (TL, TR, BR, BL) x (x f32, y f32) } (35 bytes per tag). At most 7 tags fit in the 256-byte body; the first 7 observations are reported.

4. Streaming

After STREAM(1, d) the device emits POSE frames without request. Command responses are interleaved with them; a host must match responses by type (and the echoed command id for ACK/NAK) and queue POSE frames. Disable on exit.

5. FPGA SPI map used by the MCU (for reference)

SPI mode 0, <= 12 MHz. Read: 0x03 a2 a1 a0 dummy d0 d1 ...; write: 0x02 a2 a1 a0 w0[7:0] w0[15:8] ... (little-endian words).

address register
0x000000 ID (0x41544731)
0x000008 CTRL
0x00000C THRESH
0x000018 STATUS
0x00001C FRAME_ID
0x000040 / 0x000044 I2C bridge command / data
0x000064 / 0x000068 TIME_LO / TIME_HI (reading LO latches HI, so the pair is coherent)
0x000060 FRAME_SUM (sum of all pixels of the last frame)
0x00002C streamer status: fifo_overflows[31:16] aborted_packets[15:0]

The frames themselves (binary mask + candidate list) do not travel over SPI: the FPGA streams them on an 8-bit strobed bus into the RP2350 (PIO + DMA), see docs/fpga.md. The tag decoder runs on the MCU (firmware/core/attpu.c) and produces the same records the old FPGA result RAM held: id, hamming distance, rotation, four corners as signed Q16.16 (x, y) TL,TR,BR,BL. The sensor frame timestamp comes in the packet header (no FT0/FT1 registers any more).

6. Flash storage

Two 4 KB slots at the end of flash, written alternately (slot = seq & 1); each commit erases and programs only the slot that does not hold the newest valid configuration, then reads it back. Slot image:

magic u32 0x31465441 ("ATF1") | seq u32 | ntags u16 | reserved u16 | 9 x f32 calibration | ntags x { id u16 | pad u16 | size f32 | pos 3 x f32 | quat 4 x f32 } | crc16 u16

(CRC-16/CCITT-FALSE over everything before it.) At boot the valid slot (magic, ntags <= 64, CRC) with the highest seq is loaded; if none is valid the defaults (fx = fy = 640, cx = 639.5, cy = 399.5, no distortion, empty map) are used. A power loss at any point of a commit leaves the previous configuration loadable (tests/test_fw_storage.py cuts power after every single byte operation).

The firmware blinks STAT as a heartbeat (1 Hz healthy, 5 Hz FPGA configuration failed), so a pulse line says "activity/status" in a form that needs no text and prints as one continuous 0.8 mm stroke (2 perimeters).     How these were made
    
 
    Each scenario is a short, purpose-built testbench in site/sim/tb/ (adapted copies of tb/*.v: same stimulus, same DUT; only signal dumping and, for the large frames, a dump window were added). The generator site/sim/gen_sim.py builds the stimulus with the same Python golden models the regression tests use (tools/golden.py, tools/dphy_stream.py, tools/tpu_prog.py), runs iverilog/vvp, checks the RTL result against the golden model (despeckle crop, candidate list, TPU tag vs the Python instruction-set simulator) and writes site/simout/waves.js. Only a chosen set of signals is dumped, and only inside the windows described for each scenario, so the whole waveform data is small.
    

    

    Frame pipeline: what each block does to a real test frame
    

    Six of the 100 rendered test frames (different categories of the dataset) pushed through the FPGA RTL, stage by stage, then through the tag unit and pose solver that run on the RP2350. Use the stage buttons or the slider; tick side by side to compare a stage with the one before it. Wheel zooms (try the despeckle stage at 8x), drag pans, double-click resets.
