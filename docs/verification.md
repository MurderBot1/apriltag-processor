## The test dataset: 100 images, 10 categories x 10

`test_images/sensor/<category>_<000..009>.png` (1280x800, 8 bit, as the OV9281 would deliver it) with ground truth in
`test_images/ground_truth.json` (per tag: projected corners, visibility, size, incidence angle, occlusion, detectability).
It is generated by `tools/make_dataset_100.py` (Blender Cycles + lens distortion + the sensor model of `tools/make_dataset.py`);
the committed frames are the reference, tests never need Blender. Generation is deterministic: fixed seeds
(`CASE_SEED`, `SENSOR_SEED`), one numpy generator per category, per-frame stratified parameters (a linspace over the 10 frames,
so each category sweeps its condition from mild to severe), rejection sampling so that every frame has at least one detectable tag.
The case list (poses, lights, occluders, sensor knobs) is stored in `test_images/cases.json`.

**Camera model of the dataset = the shipping lens** (`tools/geom.py`): Commonlands CIL023, EFL 2.2 mm, on the OV9281 at 3 um pixels. The frames are the sensor's full
1280x800, so there is no scaling: fx = fy = 2.2 mm / 3 um = 733.33 px, cx = 639.5, cy = 399.5, HFOV 82.2 degrees (VFOV 57.2). Distortion is OpenCV k1 = -0.126, k2 = k3 = p1 = p2 = 0:
k1 is chosen so that the -5 % TV distortion of the datasheet comes out (TV taken as the sag of the top picture edge, corner height minus edge-midpoint height, divided by the full picture
height at the edge midpoint; this definition is my reading, the lens page does not define it, so the real k1 can differ and must be calibrated). The same values are in
`config/camera_calibration.json`, which the pose tests, host library and firmware tests load. Blender still renders an ideal pinhole canvas (1920x1200, f = 640 px) and
`tools/make_dataset.py:distortion_maps` resamples it through the distortion model. The ground truth marks a tag outside the frame when any corner ray is beyond the point where the polynomial folds back
(tan(theta) > 1.63, about 58 degrees; `tools/dataset_gt.py:fold_radius`): beyond it the OpenCV polynomial projects to false in-frame pixels. Poses and seeds are the same as the earlier
90 degree set (`cases.json` did not change); only the optics changed, so tags are about 14.6 % larger in pixels and fewer are in view (570 detectable tags against 647). The firmware default calibration
(fx = fy = 640, `at_app_t` before the first `set_calibration`) is a placeholder and was left unchanged; load `config/camera_calibration.json` to match this dataset.

| category | condition (parameter sweep over its 10 frames) |
|---|---|
| `normal` | clean baseline: nominal light, plain walls, distance 0.8 ... 3.8 m (log spaced) |
| `bright` | over-exposed: light x2 ... x5.5 |
| `dark` | under-exposed: light x0.25 ... x0.03 |
| `lowcon` | low contrast: sensor-side contrast compressed to 42 % ... 24 % around mid-grey |
| `grad` | uneven illumination: strong left/right light gradient, alternating sign, |shift| 2.5 ... 5.5 |
| `shadow` | harsh cast shadow: one spot light, an occluder shadows 10-90 % of a tag |
| `noise` | high sensor noise: sigma x2 ... x4.5 of the nominal model |
| `clutter` | busy background (checker / stripes / brick / busy textures) + 3-22 occluding boxes and spheres |
| `blur` | defocus / motion blur: extra Gaussian sigma 1 ... 3 px, tags 0.9-2.2 m away |
| `persp` | perspective: tag plane tilted 15 ... 74 deg, alternating yaw / pitch and sign, 1.2-3.0 m |

### Reference detector per category (`tools/reference_pipeline.py`, `results/reference_baseline.md`)

A frame *succeeds* when every ground-truth-detectable tag is found and no false id is reported. Measured (python 3.12,
pupil-apriltags 1.0.4): `normal` 10/10, `bright` 10/10, `dark` 9/10, `lowcon` 9/10, `grad` 10/10, `clutter` 8/10, `noise` 10/10,
`blur` 9/10, `shadow` 7/10, `persp` 7/10. 560 of 570 detectable tags found (98.2 %), median corner error 0.31 px,
median camera position error 0.7 mm (p95 7.9 mm, max 19.8 mm). The 5 "false ids" are tags whose corners are 0.2 to 2 px inside the 2 px border margin of the ground-truth `in_frame` rule, which the detector still reads; none is a wrong id.
The dataset is rendered with the shipping lens model (CIL023, 82.2 degrees, -5 % TV distortion, see below); the earlier 90 degree set had 647 detectable tags, 630 found by the reference.

### Whole-pipeline accuracy (RTL simulation of the chip -> firmware solver -> ground truth)

Chip (CSI-2 at 120 fps timing, simulated RTL as it is in this branch) -> tag estimates over SPI -> C pose solver, versus the reference
detector on the *same* 100 images (`tests/run_chain_dataset.py`, `tests/analyze_chain.py`, `results/rtl_chain_results.json`;
re-run on the CIL023 dataset: 344 s for the 100 frames with 12 workers):

| category | detectable tags | chip detects | pose t median / max (mm) | reference t median (mm) |
|---|---|---|---|---|
| normal | 52 | 52 (100 %) | 1.9 / 7.0 | 0.8 |
| bright | 78 | 77 (99 %) | 1.5 / 5.5 | 1.2 |
| dark | 59 | 59 (100 %) | 1.3 / 4.2 | 0.5 |
| lowcon | 54 | **1 (2 %)** with reset values, **54 (100 %)** with THRESH ratio 1 or 2 | no pose / 1.7 / 24.0 | 0.7 |
| grad | 66 | 66 (100 %) | 1.5 / 3.4 | 0.5 |
| shadow | 42 | 38 (90 %) | 4.6 / 44.9 | 3.6 |
| noise | 50 | 50 (100 %) | 2.1 / 13.9 | 1.1 |
| clutter | 51 | 47 (92 %) | 1.5 / 11.7 | 0.5 |
| blur | 52 | 49 (94 %) | 3.1 / 11.9 | 1.0 |
| persp | 66 | 62 (94 %) | 1.4 / 3.9 | 0.7 |
| **all** | 570 | **501 (87.9 %)** | | reference 560 (98 %) |

0 false-id detections, no dropped frames (single-frame runs). These numbers are with the noise-robust labeller (`rtl/run_ccl.v`: 256 runs
per row, ~3 clocks per run on the common path, label recycling, the 64 largest candidates by area; CCL flags are diagnostics of a degraded
frame, never a rejection). Before that rework the same harness gave **450 / 647 (70 %)** on the earlier 90 degree dataset: dark 72 %, noise 70 %, shadow 68 %, clutter 14 %.
The `lowcon` weakness (0 % with the reset values) was traced to the tile ratio test `2*diff >= max`, not to the 24-level margin: with the new THRESH `ratio`
field set to 2 or 1 the chip detects 54 / 54 (see `results/lowcon_ratio.md`). The reset value stays 0 because the ratio tests 3x / 4x cost `noise` frames (50 -> 29 / 19 of 50) through labeller row drops. The firmware therefore picks the ratio per frame (`firmware/core/atratio.c`, on after boot): ratio 1 after 3 tagless frames, back to 0 on a CCL `row dropped` flag, with lockout and backoff. Simulated on the measured per-frame chain results (`tools/auto_ratio_sim.py`, `tests/test_fw_ratio.py`, `results/auto_ratio.md`): lowcon 66 / 66 in steady state after 4 lost frames at the scene start, every other category identical to ratio 0 (562 + 66 = 628 / 647 in steady state; noise stays 57). The switching latency is modelled, not measured on hardware.
The chip now misses only a few tags in `blur`, `persp` and `shadow` (small / grazing / shadowed tags).
CCL status flag set on 6 of the 100 frames (candidate table full, i.e. more than 64 candidates, only the 64 largest kept), no dropped rows.

**Architecture A3 (tag unit on the MCU), same 100 frames, full RTL chain (`tests/run_chain_dataset.py`, 344 s with 12 workers) then the C tag unit on the
packets that leave the FPGA bus: 501 / 570 detectable tags, per category identical to the table above.** (The bit-identity with the old all-FPGA run was measured on the earlier 90 degree dataset; the C tag unit equals the instruction-set simulator word for word on the 100 current frames, `tests/test_fw_tpu.py`.) This is measured (simulation), not estimated.

Tag-unit time on the MCU (**estimates**: `tools/m33_cycles.py`, Unicorn runs the Cortex-M33 machine code of the -O3 build and a static latency table costs it;
150 MHz, one core; not measured on silicon; `results/tpu_c_m33_cycles.md`): median 1.59 ms, p95 6.3 ms, worst 9.3 ms (optimistic model 1.25 / 7.4, pessimistic
1.89 / 11.0). The old FPGA processor needed a median 427k clocks = 5.0 ms and a worst 2.55 M clocks = 29.8 ms at 85.714 MHz. Pose solver
(`tools/m33_pose_cycles.py`, estimate, bracketed because the emulator has no RP2350 double-precision coprocessor): median 1.8 ms / worst 3.6 ms with single-precision
maths on the FPU, median 3.0 / worst 8.8 ms with software doubles; the real firmware (doubles through the SDK, DCP) lies in between.

Frame drops, current firmware (3 frame buffers, buffer released after the tag unit; ESTIMATE from the emulated M33 and the model in `tools/frame_budget.py`, not measured on hardware): 0 of 2000 frames lost in the nominal cycle model, 20 of 2000 (1.0 %, the slowest frame of one category recurring every 10th frame) in the pessimistic model; first build (2 buffers, release at the end) 3.0 %. Tests: `tests/test_fw_sched.py` (the C buffer pool, the order of release in `at_app_poll`, drop counting, and the C pool driven with the model's timing loses exactly the packets the model predicts, 24 cases). Details and the unverified items (late claim at the rising edge of `mcu_fs`, bus arbitration) in `results/frame_budget.md`. The text below describes the first 2-buffer build and is kept for comparison.

Frame drops of the first build (`tools/frame_budget.py`, `results/frame_budget.md`; model of 2 frame buffers, the 10 frames of a category repeated; ESTIMATE): the old design lost
20 of 100 frames (clutter 7, noise 6, dark 3, grad 2, shadow 2) if the stream looked like them. New, tag unit only, nominal model: 1.0 % overall (noise 9.9 %,
every other category 0), pessimistic model 2.0 %; with the pose solve on the same core (float): 3.0 % (dark and noise 10 % / 20 %), software doubles 4.0 %;
two cores alternating frames: 2.0 % (float pose). A third 132 KB frame buffer brings the nominal model to 0 % except software-double pose on one core (1 %) (pessimistic: 0 % for the tag unit alone and for two cores, 1 % / 2 % for one core with float / software-double pose) -
it would fit the 520 KB SRAM on paper (3 x 132 KB + 57 KB tables + 12 KB), not built. The dropped frames are the single slowest frame of a category recurring every
10th frame. Clean frames keep 120.08 fps with no drops (`test_chain.py`).

CCL-only checks (`tests/sweep_ccl_rtl.py`): the RTL candidate table equals the streaming model `golden.stream_components()` (same order); on a
historical 500-frame set (no longer in the repository) at the real 686-clock line 493 of 500 frames were identical, 7 lost 1-5 rows, peak
live labels 167 (258 with dropped rows), slowest row 590 clocks for the busiest frame (113,759 runs). On that historical set the chain
found 2651 of 2825 tags (93.8 %) with 0 false positives, up from 2158 (76.4 %).

## Continuous integration (GitHub Actions)

| workflow | trigger | what it runs |
|---|---|---|
| `dataset-<category>.yml` (10 files: normal, bright, dark, lowcon, grad, shadow, noise, clutter, blur, persp) | pull requests | `tests/ci_category.py <category>` through the reusable `dataset-category.yml`: the 10 frames of that category through the **reference detector** (undistort + pupil-apriltags). Reports `category X: N/10 detected` in the job summary and as one create-or-update PR comment per category (`tools/ci_report.py`, `pull-requests: write`; PRs from forks have a read-only token, so the comment is skipped with a notice and the summary still has the result). Each category is its own check. |
| `tests.yml` | pull requests, pushes to main | `tools/ci_all_tests.py`: `tests/run_all.py --quick` (every pytest group incl. the RTL testbenches via Icarus Verilog and `tb_clock`), `tests/test_i2c.py`, the long RTL simulations `tests/test_csi2.py` + `tests/test_chain.py`, `api/python` tests, `make -C api/cpp test`, `api/java/build.sh`, `cargo test` (api/rust) and a check that `api/testdata/golden_frames.json` is reproducible. Pass/fail counts per suite in the job summary and one PR comment. |

The dataset workflows use the model-level (PC reference pipeline) detector because the RTL chain costs about 40 s per frame
(`tests/run_chain_dataset.py`, 572 s on a 24-thread desktop for the 100 frames) - too slow and too variable for per-PR checks. The
category counts therefore describe the dataset and the reference detector, not the chip; run `tests/run_chain_dataset.py` +
`tests/analyze_chain.py` locally for the chip numbers above. **Not run in CI** (also stated in the workflow report):
`tests/run_chain_dataset.py`, the Blender generation, and the FPGA / PCB / MCU toolchain flows (yosys, nextpnr, KiCad, Pico SDK).
`tests/rtlutil.py` and `tests/atcore.py` use `iverilog`/`gcc` from `PATH` on Linux (the Windows dev box keeps using MSYS2 and the committed .dll files).

## Timing and resources (measured)

120 fps: FS-to-FS period 832,800 clocks @ 100 MHz = **8.328 ms = 120.08 fps**, no dropped frames in multi-frame runs.
Per frame (100-frame set, 100 MHz chain run): the CCL status flags are diagnostics only (6 frames set one, none dropped a row); the tag unit time is an MCU estimate, see above. Historical 500-frame
set at the real 686-clock line: slowest CCL row <= 686 clocks in 485 of 500 frames, `done` 185 clocks (median) to 2738 (worst) after the last row.

FPGA (yosys + nextpnr-ecp5, shipping part LFE5U-25F-8BG381I, speed 8): 13,389 LUT4 (55 %), 56 of 56 block RAM (100 %), core clock 92.27 - 94.91 MHz and D-PHY clock 206.06 - 226.71 MHz, 7 of 7 seeds close both (pinned OSS CAD Suite 2025-09-01, main 828bf22; `results/fpga_speed_grades.md`). Measured earlier on the LFE5U-45F with older RTL and tools (MSYS2 yosys 0.66 / nextpnr 0.7): 12,227 LUT4 (27 %), 56 of 108 block RAM, core 81.7 - 91.0 MHz (4 of 6 seeds close 85.714), D-PHY 201.5 - 217.5 MHz; see `docs/fpga.md`. Nothing is signoff and nothing has run on a device.
